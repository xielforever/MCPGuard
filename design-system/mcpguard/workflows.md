# 跨页面交互与状态规范

版本：1.0.0。视觉与组件见 [MASTER.md](MASTER.md)、[components.md](components.md)。以下定义目标 UX；是否开放操作仍取决于真实契约、当前权限与已启用能力，不新增 API 或后台任务。

## 1 必须分别表达的事实

| 对象 | 用户需要知道 | 不得据此推断 |
| --- | --- | --- |
| 申请与决定 | 谁为哪个冻结计划作出什么决定 | 已批准即已执行、已创建账号 |
| AccessGrant | 是否完成核验且当前允许授权 | 客户端已经有文件或已激活 |
| ProvisioningJob | 开通、核对、清理进度与证据 | 已核验必然仍 ACTIVE、清理完成必然全部撤权完成 |
| 文件/租约 | 此包的当前有效性与期限 | 本地存在即有效、密文可离线绕过撤权 |
| DownloadTicket | 一次领取资格是否消费 | CLAIMED 即已下载完整文件 |
| CredentialContext | 当前登记客户端的上下文是否仍有效 | 所有资源和历史文件均已激活 |
| ContextActivation | 此 Context 中哪一资源与文件已激活 | 激活即获得持续有效的执行票据 |
| Action / Execution | 请求阶段、派发及副作用证据 | 错误等于无影响、取消等于回滚 |
| 撤销、在途停止、原生清理 | 三个范围各自是否已确认 | 单一绿灯代表全部完成 |

业务枚举文案见 [state-labels.json](state-labels.json)。该文件按对象分组，不因字符串相同就共用含义，也不作为客户端自行推导权限的状态机。

## 2 登录、身份与对象范围

1. 浏览器通过自己的受保护登录建立会话。MCP Bearer、客户端 Context 或知道对象 ID 都不替代浏览器身份。
2. 页面显示可信的组织/人员标识和当前视角。管理员、审批人、申请人等是界面职责描述，不隐含新增后端角色。
3. 列表、对象详情、参数、结果、审计、导出各自按当前资格读取。入口链接可转发，但不授予任何访问权。
4. 切换认证账号、组织或退出后立即清空旧快照、选择、分页游标和敏感草稿。浏览器历史/BFCache 恢复时先重新校验，不短暂闪现上一用户数据。
5. 401 进入重新认证；403 说明当前范围不可访问并清除受限内容。网络失败显示资格未能确认，不能自行认定已撤权，更不能继续提交决定。

姓名、资源别名、原生用户名、包文件名、RPC ID 不能用作主体隔离键。正式页面不保留预览的样例身份切换按钮。

## 3 受控写申请与他人审批

| 步骤 | 用户所见与允许动作 |
| --- | --- |
| 发起申请 | 受控工具产生冻结计划；显示“已提交，尚未执行”和请求 ID，不把 MCP 平台确认当企业批准 |
| 申请人查看 | 可查看本人有权内容；只有当前服务端允许才显示取消；不出现自批入口 |
| 合格他人审阅 | 看清人员、精确资源、参数、前后变化、观察时点、范围与上限；必要细节不可见时不可批准 |
| 提交决定 | 使用当前计划与版本提交；确认框说明“只记录决定” |
| 已批准 | 显示“已批准，等待原申请者显式恢复”；审批页不新增执行或代为恢复按钮 |
| 恢复与执行 | 由原调用者走已支持入口，服务端重验身份、授权、计划、版本和期限；页面读取真实结果 |
| 结果展示 | 业务阶段、派发证据与副作用分别列出；只读查询不产生第二次执行 |

当前旧受控写决定接口接收 `vote` 与 `planHash`，并通过请求头接收版本/幂等条件，不接收文本理由。目标 UX 要求拒绝理由明确记录；这是后续迁移缺口 UX-G01，不能擅自向旧接口塞入未知字段，也不能把前端草稿写成“服务端已存”。旧入口原有行为继续保留，不能因设计阶段新增空壳操作。

## 4 资源账号和权限申请

1. 从当前主体可见的资源目录选择具体资源 ID、配置版本与权限套餐。两套 PG 即使同名，也须看清资源 ID、归属、范围与权限版本。
2. 使用服务端支持的套餐、期限与用途申请。不得输入权限 SQL、自报原生身份或复制共享管理员凭据。
3. 申请详情保留原始请求快照。合格他人可批准原范围或明确收窄；不得扩大套餐、期限或覆盖原申请。
4. 当前 v0.2.7 `DecisionInput` 对批准和拒绝均要求 `reason`（1–500 字符）；批准另需 `approvedExpiry`，拒绝不携带该字段。前端遵从真实契约，不沿用预览中“理由选填”的演示文案。
5. `AccessRequest.APPROVED` 仅表示决定已记录。授权可能仍为 `PROVISIONING`；`ProvisioningJob.VERIFIED` 也须结合最终当前 AccessGrant 判断，不能直接显示访问已开通。
6. `PROVISIONING_UNKNOWN`、任务 `OUTCOME_UNKNOWN` 或清理待确认时，只展示核对、受支持重试的只读状态或联系运维。恢复不换名重建账号，不新建授权或新建申请来掩盖未知结果。
7. 当前 Grant 确认为 ACTIVE 后，才按能力提供准备私有交付入口。批准、开通、交付、激活各有独立时间与来源。

旧失败与清理记录保持可查；重新申请是新意图，必须显式关联旧申请，不让用户误以为把旧终态直接改回可用。

## 5 加密引用包与一次私有领取

正常路径：当前 ACTIVE 授权 → 准备交付 → 本人/登记客户端的私有领取 → 完整接收与校验 → 本地安全缓存 → 服务端激活。

网页中的“下载/领取”入口须明确交付方式。自动方式展示“交给已登记客户端私有领取”；手动方式提供安全步骤。浏览器 Cookie 不授权访问原生 helper 的私有 API，不能通过页面 JS 把员工 token、Context token 或交付证明拼进 URL/DOM/日志。

| 情况 | UX 必须说明 |
| --- | --- |
| Ticket READY | 待指定主体/客户端私有领取；不是免认证链接 |
| Ticket CLAIMED | 领取资格已消费；完整到达需客户端完成回执或等价可信状态确认 |
| 消费后网络中断 | “领取结果待核对”；先检查当前包/客户端记录，不创建新原生账号 |
| 客户端无文件但包仍有效 | 通过受支持恢复方式申请新 ticket，交付同一包；不覆盖历史文件 |
| Ticket 到期/取消 | 只终止该领取窗口，不能显示整个授权已失效 |
| 文件/授权已撤销 | 不允许以重新领取、续期、重建 Context 恢复旧权限 |
| 密文损坏或本地缺失 | 显示本地不可用原因；不删除全局授权或擅自删除历史包 |

网页只展示包 ID、租约状态、期限、交付方式、客户端安全标识等经授权元数据。不提供“查看密文/解密内容/复制全部请求头”；密文虽然不可直接读出密码，也不属于可以进入模型、审计或普通日志的内容。

## 6 多资源激活与续期

客户端总览至少分别显示：当前人员认证、登记客户端、Context、每个资源的当前选定文件及激活状态。一个 Context 可激活多资源；A 资源异常不能被显示成 B 资源也已失效，除非上层公共 Context/身份确已失效。

| 失效对象 | 显示与恢复 |
| --- | --- |
| 员工认证 | 要求可信登录/私有认证恢复；旧 Context 不移交给新用户，不继承旧激活 |
| Context 自然到期 | 通过受支持的私有重新连接流程创建新 Context，再验证仍有效的文件；不直接把旧 EXPIRED 改回 ACTIVE |
| Context 被显式撤销 | 明确要求私有修复，不静默自动重建；不得复活已经撤销的包/授权 |
| 凭据自然到期 | 只有当前授权、版本和策略仍允许时申请后继包；显示新旧关联，不原地延长旧文件 |
| 单资源文件被撤销 | 关闭对应激活；保留其他资源的独立状态，不从旧历史文件中随机补选 |
| 本地文件缺失/损坏 | 指向安全组件的恢复流程；网页不要求把凭据内容粘贴给模型 |

客户端是否自动同步、是否需要重新连接、是否支持多资源，来自其实际能力声明。原生 HTTP helper、stdio 私有模式与 URL-only 的行为不同；没有私有钩子的客户端不能显示“已自动下载/已自动激活”。网页读取状态不等于启动了后台 worker。

## 7 吊销范围与结果

在提交前明确目标及影响：单文件/租约、单客户端 Context、单资源授权、用户/资源级权限分别处理。不能用一个“全部断开”按钮代替作用域选择。

确认层分别列出：将拒绝哪些后续访问、涉及哪些文件与激活、在途操作是否已知、原生账号是否托管及其清理状态。读取不到的影响显示“未知/未取得”，不能填 0。

提交后最少分三行展示：

1. 网关授权：撤销是否已持久提交、作用域及时间。
2. 在途停止：未派发、请求停止中、已确认停止或仍待核对，依据实际接口证据。
3. 原生清理：无需处理、待清理、已确认或需人工处理。不能删除/重命名外部 PREEXISTING 账号来“完成清理”。

尚未开放完整吊销 API 的部署仅展示支持的状态或明确未开放，不伪造操作成功。删除本地文件或关闭网页不等于服务端撤权，复制密文也不能延长已撤销授权。

## 8 并发、网络与前端异步状态

前端的 `正在提交/结果待核对/离线/缓存过期` 是界面读取状态，**不新增后端枚举**。尤其“决定提交响应丢失”与业务 `OUTCOME_UNKNOWN` 分开显示：前者不代表数据库业务写入已经派发。

| 情况 | 处理方式 |
| --- | --- |
| 双击 | 禁用重复按钮；同一意图保留同一业务幂等键，不生成第二个决定 |
| 提交响应丢失 | 先读取同一对象/命令状态；仅在既有契约允许时用同键同载荷核对管理提交，不重放业务 |
| 版本冲突 409/412 | 按接口错误类型展示“内容已更新，请重新审阅”；刷新，不自动改版本覆盖提交 |
| 缺少条件 428 | 展示客户端提交条件缺失，记录缺陷；不能去掉条件重发 |
| 理由/期限变更 | 形成新的用户意图和请求键，不能用同键改载荷 |
| 客户端超时 | 不自动把对象置为 FAILED/EXPIRED；区分是否已收到服务端明确结果 |
| 多窗口/后台回到前台 | 重新读取当前资格和对象版本；旧快照不能成为继续决定的依据 |
| 新请求切换或详情乱序返回 | 响应绑定组织/主体/对象/请求代次；迟到响应不得覆盖当前选择 |

前台状态页可采用有界读取刷新，建议起始 5 秒、失败逐步退到 30 秒，单页只保留一个进行中的刷新；这是 UX 默认建议，不是后端 SLO。后台暂停非必要轮询，回到前台先重验。终态停轮询，私有组件按自己的有界同步驱动运行，不由网页虚构后台循环。

## 9 结果未知的核对

页面持续突出“请勿重复提交”，展示固定计划、派发证据、原生回执关联、观察时间、能证明和仍未知的部分。只有有资格者能发起接口明确支持的只读核对。

当前业务值与目标值相同，不足以证明某次写已经执行。人工备注不覆盖原始证据。没有一键重试、换名建号、重新领取业务执行权或“标记未执行并重做”。后续新意图须先处理原不确定性并按原设计重新授权。
