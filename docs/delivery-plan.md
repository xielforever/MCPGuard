# MCPGuard 交付计划与验收追踪

状态：正式设计初稿 v0.1，待评审；本文件描述拟议交付，不表示功能已实现。日期：2026-10-22。

实现进度：已交付 [第一条真实 PG 读取闭环](read-slice.md)，验证见 [2026-10-22 记录](validation/read-slice-2026-10-22.md)。该增量覆盖两入口、测试主体、权限隔离与持久审计，不代表 P1 企业 OAuth、P3 全部适配或 P4 写入审批已经完成。

## 1 已确认边界与交付目标

产品是单企业集中网关，服务多人、多组或项目、多种受管资源；资源位于企业服务器和员工本地，连通条件已具备，不安排网络建设工程。

两条入口都是 v0.1 产品目标：IDE 原生 HTTP MCP 直连；IDE 经本地 stdio 接入程序转 HTTP，进入同一企业 MCP 网关。可以先后开发，但最终必须分别验收，不能把第二条作为未承诺的附加能力。

MCP 仅用于 IDE 到网关。网关通过 PostgreSQL 驱动、Redis RESP 和 HTTP 客户端直接访问原生服务；不把原生服务改成 MCP Server，也不设计下游 MCP 认证或版本协商。

目标闭环是：可信主体 → 工具发现 → 资源与参数校验 → 不可变操作计划 → 策略与所选人类授权 → 原生派发 → 实际结果与副作用状态 → 可追溯审计。

代码现有 stdio 代理、确认与页面不能视为该架构已经实现。现有构建或缺陷复现通过，也不能替代新架构的验收。

详细契约分别见 [MCP 接入与执行边界](mcp-protocol-design.md)、[IDE 接入兼容](ide-access-compatibility.md)和[原生服务适配](native-adapter-design.md)；本计划负责阶段依赖与验收关联。

无害 fixture、模拟身份和协议契约可先用于设计验证；不能据此默认连接生产服务、开放任意命令或使用全企业管理员凭据。

## 3 分阶段交付

### P0 设计与契约基线

交付产品范围、角色与资源模型、两入口边界、协议 profile、工具 Schema、操作计划、状态机、结果与错误契约；说明已确认项、候选项和 D-01 至 D-06。

区分 RPC ID、action ID 与 execution ID；固定参数与目标绑定、撤权及取消竞争、派发前终止和派发后未知的处理。普通等待、MRTR 或其他续传仅在所选 profile 和客户端实际支持时采用。

退出条件：至少一条读取和一条候选受控写路径从入口到审计完成桌面推演，并能追踪到验收编号；不存在依赖自然语言 approved 字段的授权。

### P1 MCP Server、身份与两条入口

依赖 P0 的入口与身份契约。建立统一 HTTP MCP Server、标准受保护资源发现与令牌验证；实现 stdio 接入程序的登录、令牌保管、流转发和生命周期映射，两入口调用同一业务处理器。

先用无害诊断工具和模拟企业授权服务完成登录、发现、调用、结果、并发及取消，不等待真实 IdP 才验证协议，也不把网页登录等同 MCP OAuth。

退出条件：独立测试客户端经两入口均取得真实网关结果；无效令牌、相同 RPC ID 的不同员工、版本不兼容及断线可以区分，stdout 不混入日志或凭据。

### P2 工具、资源、策略与持久状态

依赖 P1 可信主体。实现受控资源和工具注册、目录权限过滤、逐次调用鉴权、结构化策略、不可变计划、持久 action 与执行领取，以及最小状态事件记录。

用无害内存执行桩贯通允许、拒绝、等待、过期、取消与结果，验证目标或参数替换无效。按已确认风险分级和他人审批测试，具体审批组未定时用fixture，不把测试组映射冒充真实企业授权。

退出条件：两个用户和两个权限范围不串目录、结果或状态；策略 deny 不被普通批准覆盖；重启与并发领取不产生额外执行权。执行桩通过不计作原生适配完成。

### P3 原生适配与首条真实服务闭环

依赖 P2 的计划、身份及状态契约。按已选最小工具目录接通真实测试 PG、Redis 和受控 HTTP 服务；先交付一条从 MCP 调用到原生读取及审计事件的完整路径，再扩展三类适配。

受控写使用隔离测试数据和明确测试策略。PG 验证只读角色、事务、参数绑定、函数与多语句限制及提交未知；Redis 验证 ACL、全部 key、连接状态和部分副作用；HTTP 验证固定 operation、认证、跳转及真实幂等语义。

退出条件：原生驱动确实访问各测试服务，类型、二进制、截断和错误映射正确；失败或取消不被直接解释为无副作用，结果未知禁止自动重试。原生认证失败不冒充网关 MCP 登录失效。

### P4 人类授权、审计与最小控制台

依赖 D-01、D-06 与 P2/P3。接通所选人类授权模式、认证审批入口和通知，完成请求详情、决定、执行领取、真实写入结果与审计查询的业务闭环。

以一条他人获批的原生写操作证明授权有效，另验拒绝、迟到批准、通知失败、撤权及参数变化不误派发。首版稳定主体ID强制不同主体；本人确认或ChatGPT自身操作确认不能代替企业批准。

控制台至少支持受权资源、我的请求、待处理授权、有效策略和审计；页面数据来自真实持久状态。审批凭据不得返回模型；审计和普通日志不包含令牌、密码或明文确认码。

退出条件：从两入口发起的授权请求都可在所选入口完成，并关联实际原生结果；通知可达不等于批准，按钮显示成功不等于后端成功，关键审计无法持久化时不派发写操作。

### P5 完整模拟联调、故障与真实 IDE 验收

依赖前述闭环。沙箱运行真实网关、两种接入客户端、真实测试 PG/Redis、mock HTTP、模拟身份与 IM，以及真实持久数据库，不需要模型 key。

从标准建连或发现开始验证读取、阻断、授权写入、结果、取消和审计；不得跳过失败握手后将局部驱动测试宣称为端到端通过。覆盖重启、重复事件、并发、凭据轮换、连接中断和写后响应丢失。

真实 IDE 验收按实际客户端、扩展版本、系统、入口、profile、身份方案、等待窗口和支持能力记录。HTTP 与 stdio 两入口各需至少一个完整真实 IDE 组合，不能用其中一个替代另一个。

标准建连、工具发现及沙箱脚本调用无需模型 key；自然语言触发与模型消费结果另用实际 IDE 模型会话验证。真实企业 IdP、所选 IM 和最终资源授权在对应环境独立核实，模拟通过不替代这些证据。

退出条件：声明支持的组合满足下表，限制已说明，发布配置可复现；实现提交、构建配置和验收证据绑定同一目标，不以候选通过或截图代替最终检查。

## 5 交付边界与变更控制

各阶段必须交付可观察的链路增量，而非仅累积框架和设计；P1 的诊断、P2 的执行桩和 P3 的原生读取分别注明替代范围，只有 P4/P5 才能证明所选人类授权到真实写入的完整闭环。

安全不变量贯穿各阶段：派发前资格检查、批准不可篡改、无权者不可读取状态、原生副作用据实表达。跨外部服务不承诺端到端恰好一次，也不把客户端重试视作新的执行许可。

工具范围、协议或授权模式变化时同步更新关联 A-ID、支持矩阵和设计文档。具体日期、容量目标和默认期限待实施评估与实测后确定，本初稿不虚构工期或完成率。
