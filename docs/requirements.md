# MCPGuard 产品需求与需求状态

版本：设计初稿 v0.1。日期：2026-10-22。范围：企业集中 MCP 网关。
本文记录目标行为及验收要求，不代表功能已经实现，也不冻结尚未决定的产品细则。

## 1 需求状态约定

| 标记 | 含义 |
|---|---|
| 已确认 | 用户已确定的产品或架构边界，不表示实现或验收完成 |
| 建议 | 本稿提出的具体行为、首版取舍或验收方式，供设计评审 |
| 待定 | 用户尚未确定的选择；相关设计保留扩展点，不自行认定已获确认 |

实现状态与需求状态分别记录。当前代码主要是早期代理、确认与控制台脚手架。
企业统一身份、原生适配、真实审批执行与审计闭环均不能依据现有界面或说明认定完成。
本稿的验收表全部是未来门槛；通过情况应由后续测试记录提供证据。

## 2 已确认的产品边界

- MCPGuard 就是一个企业 MCP 网关系统，集中提供接入、身份、权限、策略、审批与审计。
- 面向多人、多资源使用，不把员工个人代理作为企业架构的默认形态。
- MCP 仅用于 IDE 到 MCPGuard；后端服务不需要实现 MCP。
- 网关通过 PG 协议访问 PostgreSQL，通过 RESP 访问 Redis，通过 HTTP/HTTPS 访问业务 API。
- 资源混合部署在企业服务器与员工本地，现有网络已互通；本稿不设计网络打通方案。
- IDE 支持两条路径：远程 HTTP MCP 直连；本地 stdio 接入程序转 HTTP 连接同一网关。
- 两条路径进入同一套企业身份、资源权限、策略、授权决策与执行流程。
- 首版按风险分级：已授权普通读取自动放行，受控写入由他人审批，高危操作默认禁止；具体敏感分类与审批组继续细化。
- 首版采用受控目录：PG模板、限定Redis命令与key范围、固定API operation，不开放任意SQL、命令或URL。
- 首发客户端已选择ChatGPT；账号/工作区、具体产品界面、profile和真实兼容情况继续验证，企业IdP与通知平台尚未确定。
- 本轮交付为正式设计文档初稿；不把设计建议写成已上线能力。

## 3 目标用户与核心场景

以下为建议的职责划分，不代表角色模型或权限粒度已经冻结。
同一员工可以承担多种职责，服务端仍逐次检查其当前授权范围。

| 场景 | 用户目标 | 目标结果 |
|---|---|---|
| 员工接入 | 在日常 IDE 中使用企业资源 | 经企业身份验证后发现并调用获授权的网关工具 |
| 资源登记 | 管理员纳管 PG、Redis 或业务 API | 资源、归属、执行凭据引用及允许操作可追溯 |
| 工具发布 | 工具管理员提供稳定业务能力 | 工具 Schema、版本、资源绑定和操作语义明确 |
| 受控操作 | 员工发起需要额外授权的调用 | 看清真实操作、等待决策，并获得明确执行状态 |
| 授权处理 | 合格决策人处理待授权操作 | 决策绑定具体计划，不能通过更换参数扩大操作 |
| 故障核对 | 操作人与审计人员排查异常 | 关联调用、授权、实际派发及已知副作用证据 |

## 4 企业核心使用流程

1. 管理员登记资源与凭据引用，配置其归属、访问范围和连接方式。
2. 发布工具定义，绑定已注册资源、原生适配器操作及策略。
3. 员工通过所选 IDE 接入路径认证，网关建立可信调用主体。
4. 网关按权限提供工具目录；调用时再次校验资源及操作权限。
5. 网关生成操作计划，策略决定允许、阻止或进入人类授权。
6. 满足执行条件后，使用原生驱动派发操作并返回标准 MCP 工具结果。
7. 调用者、授权决策、资源、执行身份和结果共同进入关联审计。

## 5 功能需求

| 编号 | 需求 | 状态与边界 |
|---|---|---|
| FR-01 | 提供统一企业 MCP 入口，支持多人调用与多资源纳管 | 已确认；具体部署拓扑属于架构设计 |
| FR-02 | 提供远程 HTTP 与 stdio 转 HTTP 两条客户端接入路径 | 已确认；ChatGPT首发HTTP接入，stdio另选实际支持客户端验收 |
| FR-03 | 将每次受保护操作关联到经验证的企业主体 | 企业统一身份为已确认主线；具体身份源与接入机制待定 |
| FR-04 | 维护原生资源目录、归属、配置版本与凭据引用 | 建议；不得要求后端实现 MCP |
| FR-05 | 由网关维护工具定义、输入输出 Schema 和原生操作绑定 | 受控目录已确认；具体工具清单、范围与Schema继续细化 |
| FR-06 | 工具发现按访问范围过滤，执行前重新校验权限 | 建议；资源、工具、数据范围等细化授权规则待定 |
| FR-07 | 策略明确表达允许、阻止、需人类授权三类结果 | 已确认风险分级；工程采用默认拒绝、DENY优先，具体分类继续细化 |
| FR-08 | 将人类授权绑定到调用者、资源、工具版本和完整操作计划 | 受控写由他人审批已确认；审批组、路由与敏感读例外待细化 |
| FR-09 | 已批准计划在派发前检查有效期、权限及相关配置 | 建议；变更影响授权语义时重新生成计划并授权 |
| FR-10 | 原生适配器执行获准的 PG、Redis 与 HTTP 操作 | 已确认协议边界；具体驱动与执行限制为设计建议 |
| FR-11 | 关联业务 action、MCP 请求尝试与实际 execution | 建议；重复决策或并发领取不得多次消费同一派发资格 |
| FR-12 | 明确表达未派发、成功、已知失败与结果未知 | 建议；不能把超时、取消或错误等同于完全未生效 |
| FR-13 | 提供真实资源、工具、请求、授权与审计管理界面 | 建议；页面与角色细则待定，不以静态样例作为交付 |
| FR-14 | 记录身份、策略、决策、计划、派发及结果的关联证据 | 企业审计为已确认主线；字段、保留期和访问范围待定 |
| FR-15 | 保护资源凭据、访问令牌、敏感参数和返回数据 | 采用凭据引用、加密详情与字段脱敏；具体托管平台与留存参数待定 |
| FR-16 | 记录每个 IDE 组合的版本、能力、限制和验收证据 | 建议；SDK 宣称支持不能代替真实 IDE 验收 |

## 6 人类授权与调用生命周期

人类授权是企业控制流程，MCP 只是 IDE 交互协议；两者状态分别管理。
首版已选风险分级；受控写入必须由他人审批，以可信主体ID检查与操作人不同，不能依赖显示名。
本人确认不作为首版受控写批准方式；ChatGPT界面的操作确认或模型approved字段不能代替企业他人审批。
审批通知渠道、审批人路由与期限仍待细化；代理审批和多人会签不作为首版默认能力。
等待期间建议不占用业务事务、锁或专属连接。
协议交互可采用有界等待或经验证的续传方式，具体方案按客户端能力评审。
不假设所有 IDE 都支持 elicitation、MRTR 或 Tasks，也不先指定无依据的统一等待时长。
普通 MCP 调用已结束且尚未派发时，迟到批准不得自行启动执行；续传须有独立契约。
同一批准最多消费一次网关派发资格，不承诺 PG、Redis、HTTP 跨系统恰好执行一次。

## 7 首版原生工具范围

以下仅为建议候选；PG、Redis、HTTP 三类协议边界已确认，具体操作尚未冻结。

| 资源类型 | 读取候选 | 受控写入候选 | 必须明确的边界 |
|---|---|---|---|
| PostgreSQL | 结构查询、参数化查询模板 | 固定写模板或业务操作 | 数据范围、角色、函数、事务、结果限制 |
| Redis | GET、有限 MGET、有界 SCAN | 受限 key 范围内的已注册操作 | 命令、全部 key、枚举可见性及连接状态 |
| HTTP API | 已注册查询 operation | 已注册业务写 operation | 固定服务、路由、身份、幂等及副作用 |

不默认开放任意 SQL、任意 Redis 命令、任意 URL 或员工自带生产凭据。
原生连接可复用，但调用主体、授权、计划和审计上下文必须保持隔离。
读取也可能涉及敏感数据或资源消耗；是否需要确认由后续策略决定。

## 8 可验证的验收要求

下表为建议验收基线，全部尚待实现和验证，不表示已经通过。
验收使用测试身份、测试数据和无害操作，不依赖真实生产凭据。

| 编号 | 对应需求 | 验收条件 |
|---|---|---|
| AC-01 | FR-01、03、06 | 至少两名员工、不同权限和多个资源；网关目录按主体过滤，越权调用拒绝；ChatGPT共享快照的元信息隔离按分组发布另验 |
| AC-02 | FR-02、16 | 两条 IDE 路径分别验证认证、发现、调用和结果；分别记录客户端版本与限制 |
| AC-03 | FR-03、15 | 登录、续期、退出和撤权可验证；跨员工令牌及共享管理员凭据不能代替身份隔离 |
| AC-04 | FR-04、05 | 已注册工具能定位资源与版本；替换 resource ID、地址或操作不能绕过授权 |
| AC-05 | FR-07、08 | 允许、阻止及需授权三种路径结果明确；批准、拒绝、过期均有可追溯证据 |
| AC-06 | FR-08、09 | 批准后替换参数、资源、工具或执行身份时拒绝或重新授权，不执行扩大的操作 |
| AC-07 | FR-11 | 重复决策、请求重试和并发领取不会重复消费派发资格；不同员工相同 RPC ID 不串结果 |
| AC-08 | FR-10、12 | 通过真实测试 PG、Redis 和无害 HTTP 服务验证原生协议，不使用模拟 MCP 后端代替 |
| AC-09 | FR-10、12 | 取消、断线和超时按协议及原生操作语义处理；不能错误宣称已回滚或自动重试未知写入 |
| AC-10 | FR-12、14 | 结果未知可检索并保留核对证据；请求失败与实际副作用状态分别表达 |
| AC-11 | FR-13、14 | 控制台读取真实状态，操作可持久化；调用、决策和执行可由同一业务标识关联 |
| AC-12 | FR-15 | 凭据、令牌及授权秘密不出现在普通日志、IDE 配置或工具结果中 |
| AC-13 | FR-10、15 | 连接复用、凭据轮换和事务清理不会泄漏其他调用的身份、配置或未读响应 |

## 9 待定项与后续维护

已确认：风险分级与受控写他人审批、受控工具目录、ChatGPT首发客户端。
待定：企业身份源、审批人路由、具体工具及数据权限、通知渠道、留存和敏感交付规则。
待核实：ChatGPT账号/工作区、界面与profile；stdio验收客户端另行选择，不由ChatGPT的HTTP通过替代。
建议：先确定工具与操作契约，再落实身份权限、计划授权、原生执行及审计验收。
性能、并发、超时、结果上限与可用性目标应依据实际场景和测试确定，不编造验收数字。
后续决定应更新本稿的状态、相关设计与验收记录，保留尚未决定事项。
