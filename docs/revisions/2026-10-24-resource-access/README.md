## 1 已确认的方案

用户确认：coding 客户端只配置 MCPGuard，登录后发现资源、申请资源账号和权限、下载加密凭据文件，后续自动使用。实际数据库连接由 MCPGuard 服务端建立，终端只取得业务结果。解密密钥、原生密码和已认证数据库连接不交给终端。撤权由服务端阻止相关文件继续产生执行资格。

完整流程为：资源登记和发布 → 按身份发现 → 账号与权限申请 → 决策 → 原生账号开通与权限核验 → 授权激活 → 加密凭据签发和下载 → 客户端自动使用 → 服务端逐次验权和执行 → 吊销、在途处置和后台清理。

资源使用授权与单次操作审批分别管理。有效授权下的普通读可以自动执行；受控写仍由合格他人批准具体操作计划，批准资源申请不自动批准业务写入。

## 4 本增量与原设计的关系

| 原设计或实现 | 本增量的处理 |
|---|---|
| 一个全局业务 PG 连接及固定 demo 资源 | 新路径改为资源注册表、按调用者和资源解析原生凭据；原 demo 路径作为版本化兼容范围保留 |
| 普遍以网关注入的 scopeId 区分用户数据 | 不再作为通用多 PG 模型；原生账号、角色、视图和 RLS 等承担资源实际配置的数据权限。scope 仅可作为特定已登记业务模板的额外约束 |
| IDE 只持网关访问令牌，不持资源凭据 | 扩展为可持服务端加密文件和独立客户端上下文；仍不持原生密码、解密密钥或审批秘密 |
| 资源上的单一 credentialRef | 变为按主体、资源、权限套餐解析的 CredentialBinding；原生身份和秘密版本分开管理 |
| Action、冻结计划、他人决定、单次领取和未知写不重放 | 继续适用；新增资源授权和凭据文件检查，不改变历史 Action 的含义 |
| v0.1 的 JSON Schema、OpenAPI、demo-tools 和 SQL 模型 | 保留其历史及既有实现适用范围；尚未表达本增量。新增机器契约在后续开发阶段单独版本化，不手工扩大旧文件含义 |
| 2026-10-23 的本机测试和原生验收记录 | 保留原文；不得作为本增量完成或客户端凭据下载通过的证据 |

当旧文档在这些条目上与本增量不同，以本增量作为后续开发目标；没有列出的受控目录、身份验证、审计、原生执行及两入口约束继续沿用。历史陈述按原日期理解，不回写成今天的实现状态。

## 5 实施边界

本轮未修改业务代码、可执行脚本、Schema、迁移或服务配置，也未重启、部署或签发任何真实凭据。现有工作区已有未提交实现，本增量不以最后一个提交代表其全部内容。

本次不开放任意 SQL、任意 Redis 命令或任意 URL，不增加返回明文密码的 download/decrypt 接口，不将客户端执行或数据库直连作为兼容回退。

企业 IdP、实际审批组、企业秘密管理产品、生产权限套餐、期限、留存及容量仍需部署时落实。可先用测试身份和受限凭据提供方推进隔离 PG 的闭环，不因这些部署参数未选型反复重做已确认的架构讨论。
