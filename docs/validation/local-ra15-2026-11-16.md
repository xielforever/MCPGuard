## 3. 覆盖与断言

| 用例 | 完成条件 |
|---|---|
| `TestControlledWriteRejectedAfterIssuerRotation` | issuer 升 version 2、换新 epoch 后，已获批准的写计划 resume 被拒，原生行不变（旧批准不执行） |
| `issuer_epoch_changed`（既有） | 旧包在换 epoch 后 `Validate` 返回 `ErrCredential`，旧包不可复活 |
| `TestControlledWriteRecoveryFenceBlocksStaleMetadata` | 原生 fence 前进而元数据记录不变（等价元数据回滚）时，已批准写计划 resume 被拒、原生行不变；运营方 `Record` 接受恢复点后新计划可执行 |
| `TestRevocationRecoveryFenceBlocksOldPackage` | 原生 fence 前进后，旧凭据在 selectGrant 阶段被拒并转 REVOKED（包资格不复活） |
| `TestRevocationAdvancesRecoveryFence` | 撤销在同一流程里推进原生 fence 并记录到元数据 recovery_fence，两侧 generation 一致 |
| RA-14 既有 | epoch 淘汰连接池、历史结果按 epoch 拒绝、在途计划不重放 |

## 4. 实现要点

- 原生 provider DDL v4：`mcpguard_provision.fence_state(org,generation)` + `advance_fence`/`fence_generation`；元数据迁移 012 `mcpguard_ra.recovery_fence`。
- fence 锚点在业务 PG（不随元数据备份恢复）：原生 generation 高于元数据记录即视为回滚，签发/领取/写派发拒绝（fail closed）。
- 撤销通过 `RevocationService.Fence` 先推进原生 fence、再在同一元数据事务记录，崩溃只会让原生侧更高（安全方向）。
- 检查接入：凭据签发/状态（`selectGrant`）、写计划复查（`WriteService.current`）、读计划复查（`ReadService.claim`）。
- 运维入口：`mcpguard-catalog restore-check <org>`（可疑时非零退出并打印 JSON）、`restore-accept <org> <actorId>`（重新核验后接受恢复点）。
- 既有 provider 环境需显式重装（DDL 校验和 v4），不会自动升级。
