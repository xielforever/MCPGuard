## 真实客户端和故障结果

- HTTP 由 Codex 调用私有请求头助手，独立 worker 完成密文领取、保存和激活。同一连接通过同 Context 续期继续读取。自然到期后，缓存请求头失效，重新连接后能用有效文件激活新的 Context。
- stdio 由 Codex 启动 `mcpguard-connect`。同一客户端下一次调用完成自然到期恢复，并用新 Context 重验保留文件。两条入口均实测将丢失的文件重领为同一密文。
- 原生账号经开通和权限观察后授权才进入 `ACTIVE`，`PROVISIONING` 阶段拒绝签发。资源授权独立于单次写审批，独立审核后还需请求者显式 `action.resume`。数据库核对一次写入，重复恢复保持版本不变。
- 撤权时先从 PostgreSQL 的活动视图确认固定 UPDATE 正在真实等待行锁。撤权事务提交后，PostgreSQL 对同一 PID 记录按请求取消语句，独立事务仍持有该锁，行版本保持 `2`。网关 Action 保留 `OUTCOME_UNKNOWN`，重试恢复未增加派发意图。另一个已审批但未派发的 Action 被拒绝，派发意图数为零。
- 提供方暂不可达时，`revocation-cleanup retry` 记录 `FAILED`。可以禁用账号但仍有真实会话时，持久回执为 `SESSIONS_REMAIN`。连接排空后再次执行，提供方确认原 OID、目标权限和零会话并记录 `CLEANED`。
- 使用 `pg_dump` 和 `pg_restore` 恢复真实的撤权前元数据副本。原生恢复代次为 `2`，备份代次为 `1`，旧上下文的执行、包签发和文件激活均被拒绝。恢复保护不改写无关租约。核对原生角色禁用状态与业务行版本后，在恢复副本补录唯一缺失的授权撤销。无关资源恢复读取，被撤销的授权继续拒绝签发。

## 复跑与部署边界

在 WSL 中用实际安装的 `codex` 绝对路径分别执行 `python3 -B scripts/ra18_client_fixture.py http --prepare --codex <路径>` 和 `python3 -B scripts/ra18_client_fixture.py stdio --prepare --codex <路径>`。场景与客户端在同一次 WSL 执行内运行，避免空闲停机释放 Docker 动态端口。使用 `--report` 可生成脱敏 JSON。私有目录保留测试日志与组件缓存。

业务写通过 `MCPGUARD_RESOURCE_WRITES=enabled` 显式启用，依赖已配置的资源读取及 Context，以及 `grant-write-runtime` 权限。清理回执需在专用环境显式应用资源元数据迁移 013 和原生提供方迁移 005。清理重试会复核历史缺少回执的 `CLEANED` 记录。
